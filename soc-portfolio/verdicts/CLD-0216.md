# CLD-0216: MFA denials without success: ops-admin@cloudora.io

Engagement: Cloudora · Shift 4 · 2026-08-29
Verdict: True positive · Severity (my rating): Low (reported Low)
QA review: Satisfactory

## Alert
Rule Repeated MFA denials fired after five MFA push denials for ops-admin@cloudora.io between 05:31 and 05:52 UTC from 192.0.2.88, an unknown hosting-provider IP. Password evaluation succeeded before MFA, but all MFA requests were denied and no successful sign-in followed.

## Hypothesis
Malicious: An attacker obtained the valid ops-admin password and attempted MFA fatigue to gain access.

Benign: The legitimate administrator repeatedly attempted to sign in from unfamiliar infrastructure and denied their own MFA requests.

## Evidence checked
Sign-in activity

KQL review of ops-admin@cloudora.io identified the MFA-denied activity from 192.0.2.88.
Source was Unknown (hosting) using Windows/Chrome.
First event at 05:31 showed password stage passed.
Fifth denial occurred at 05:52, followed by no further attempts.
No successful authentication was identified during or after the attack.

IP scoping

signin
| where IP == "192.0.2.88"
| order by Timestamp asc
Returned only the ops-admin MFA-denial activity.
No other Cloudora accounts were targeted from the IP.

Successful-access search:

signin
| where IP == "192.0.2.88"
| where Result =~ "Success"
| order by Timestamp asc
Returned no rows.
No successful authentication from 192.0.2.88 was identified.

A database-wide search for 192.0.2.88 returned only the same sign-in events with no evidence of follow-on activity.

Threat intelligence

External reputation by AbuseIPDB review showed previous reports associated with DDoS/web attacks and open SOCKS proxy activity.
This was treated as supporting intelligence, not standalone proof.
The Shift 4 intel digest specifically warns of MFA fatigue against operations accounts from hosting infrastructure where the attacker already possesses a valid password.
The brief also states that MFA denials without a successful sign-in still mean the credential is burned.

## Action
Immediately reset the ops-admin password because the successful password evaluation confirms the credential is compromised/burned.

Revoke all active sessions and refresh tokens for ops-admin and invalidate existing authentication cookies so previously established sessions cannot continue using old session material. Require fresh authentication with the new password and MFA.

Block 192.0.2.88 from accessing Cloudora resources and add it to the internal malicious IOC/blocklist. Continue monitoring for attempts from related infrastructure or attempts against ops-admin from new IP addresses.

Review recent ops-admin authentication and privileged activity for evidence that the compromised password may have been used successfully from another source.

Flag the activity to the vCISO as useful threat intelligence because an operations/admin credential was compromised and used in an MFA-fatigue attempt, even though the attacker did not successfully authenticate.

## Justification
KQL confirmed repeated MFA denials against ops-admin@cloudora.io from 192.0.2.88, an unknown hosting-provider IP.

signin
| where IP == "192.0.2.88"
| order by Timestamp asc

The activity was limited to ops-admin. Authentication evidence showed password stage passed, meaning the correct password was successfully presented before the attacker reached MFA. Five MFA pushes were denied, with the final denial occurring at 05:52 UTC.

A search for successful authentication from the suspicious IP:

signin
| where IP == "192.0.2.88"
| where Result =~ "Success"
| order by Timestamp asc

returned no rows.

A database-wide search for 192.0.2.88 returned only the same sign-in activity. No other targeted accounts or follow-on activity were identified in the available telemetry.

External reputation checks also showed previous reports involving DDoS/web attacks and open SOCKS proxy activity. This was treated as supporting threat intelligence rather than standalone proof. The observed Cloudora authentication activity itself provides the primary evidence supporting the malicious assessment and decision to block the IP.

The activity also directly matches the Shift 4 intel digest, which warns of MFA-fatigue attacks against admin/operations accounts originating from hosting infrastructure with a valid password already in hand. The brief specifically states that MFA denials without a successful sign-in still mean the credential is burned.

The verdict is therefore True Positive with Low severity. The attack progressed beyond password evaluation and demonstrated compromise of a valid operations/admin credential, creating limited security impact. However, MFA prevented successful authentication, no malicious session was established from 192.0.2.88, no system or data access was identified, and the activity was bounded to one account.

The formal escalation threshold is not currently met, but the activity should still be reported to the vCISO as relevant threat intelligence.

## Tuning note
No tuning recommended. The rule correctly detected malicious MFA-fatigue behavior.

Continue alerting on repeated MFA denials, particularly when password evaluation succeeds, the source is hosting infrastructure, or a privileged/admin account is targeted.
