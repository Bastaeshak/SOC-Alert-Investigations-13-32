# CLD-0231: Token issued before reset still in use: marcus.oje@cloudora.io

Engagement: Cloudora · Shift 8 · 2026-09-04
Verdict: False positive · Severity (my rating): Informational (reported Low)
QA review: Excellent

## Alert
Rule “Refresh token predating credential reset” fired after a refresh token issued to marcus.oje@cloudora.io on 2026-10-08 at 08:19 UTC was successfully exchanged for a new access token on 2026-10-14 at 04:52:08 UTC, after Monday's credential reset. The response record shows session revocation was applied only to Daniel Reeve and Eleanor Walsh, not Marcus.

## Hypothesis
Malicious: An attacker retained access to Marcus's pre-reset refresh token and successfully reused it after the credential reset because Marcus's sessions were not revoked.

Benign: Marcus's legitimate registered laptop retained its pre-reset refresh token and exchanged it normally after the reset because his sessions were never revoked. The alert therefore exposes a remediation gap rather than malicious use of the token.

## Evidence checked
Reviewed Marcus's complete signin timeline and post-reset activity. His normal session on Oct 8 at 08:20:47 UTC originated from 203.0.113.10, London, using his registered Windows device. A malicious session was separately observed on Oct 8 at 23:57:12 UTC from known attacker IP 192.0.2.146, where an inbox rule was created and is tracked separately under CLD-0232. After Monday's remediation, 192.0.2.146 attempted access again on Oct 13 at 05:11:50 UTC, but Conditional Access blocked the attempt under CLD-0225. The CLD-0231 token exchange on Oct 14 at 04:52:08 UTC originated from the same normal London IP 203.0.113.10 and Marcus's registered Windows device. No successful post-reset activity from the known attacker infrastructure or an unfamiliar device/source was identified

## Action
Close CLD-0231 as False Positive for malicious token use because the successful exchange matches Marcus's established legitimate device and network baseline. However, immediately revoke Marcus's remaining sessions/tokens because the event proves his pre-reset refresh token survived Monday's credential reset. Review the entire Monday remediation list and verify session revocation for every in-scope account rather than limiting remediation to the accounts that generated alerts; the response record currently shows revocation only for Daniel Reeve and Eleanor Walsh. Investigate whether any other pre-reset sessions/tokens remain valid and revoke them where required. Re-raise if a surviving token is successfully used from attacker infrastructure, an unknown device/location, or produces unauthorized follow-on activity.

## Justification
The underlying 04:52:08 UTC token exchange is legitimate, despite the detection correctly identifying that the token predates the credential reset. Marcus's Oct 14 exchange came from 203.0.113.10 in London on his registered Windows device, matching his established legitimate session on Oct 8 from the same IP, location, and registered device. Post-reset scoping identified only one event from known attacker infrastructure: 192.0.2.146 attempted Marcus's account on Oct 13 at 05:11:50 UTC, but Conditional Access blocked that attempt. No successful post-reset attacker token use was identified. Therefore, the current alert does not establish malicious use and is False Positive / Informational.

The alert does, however, confirm a real remediation gap. Marcus's token was issued before the credential reset and remained valid afterward because session revocation was not applied to his account. The surviving token must therefore be remediated even though its observed use in CLD-0231 was legitimate.

## Tuning note
Do not suppress this rule. It successfully identified a genuine containment/remediation weakness that would otherwise have been missed. Keep alerting when tokens issued before credential resets remain usable afterward. If enrichment is available, include the source IP, registered-device status, token issue time, reset time, and whether session revocation was actually completed.
